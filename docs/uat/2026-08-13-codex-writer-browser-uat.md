# Codex writer 服务端权威控制 UAT

- 日期：2026-08-13
- 被测环境：生产 Fleet Dashboard，Mac Mini M4（mesh `100.64.0.2`）
- 被测版本：`8cffd96` / Dashboard PWA v116
- 修复后回归版本：`4252635` / Dashboard PWA v117
- Fleet 操作入口：已登录的真实浏览器页面
- 外部 writer：在 `.2` 上启动的真实 Codex CLI
- 测试数据：仅使用名称含 `UAT writer control` 的专用会话

## 验收边界

1. 所有用户可见操作必须从浏览器完成：创建会话、发送、排队、选择动作、刷新、释放和恢复写入。
2. Shell 只用于启动/终止 `.2` 上的外部 Codex 测试夹具、模拟 agent 断线，以及在 UI 已给出结论后采集服务端证据；不能代替浏览器判断通过。
3. 不操作 `peace 1.4` 或其他业务会话，不修改仓库文件，不执行强制接管其他真实任务。
4. 每个用例以浏览器可见状态为主断言；服务端快照、writer lock、rollout 和日志只作为辅证。

## 通过标准

- 浏览器不自行推断 writer、turn、access、queue 或审批状态。
- 外部 Codex 持有 writer 时，Fleet 能浏览和服务端排队，但不能 steer、停止或审批外部 turn。
- 队列状态、按钮与刷新恢复完全一致；按钮只出现服务端允许的动作。
- writer 释放、进程异常退出或 agent 重连后，页面在规定时间内恢复，不能留下长期非法占用。
- 无重复用户消息、无错误的“Codex 可接管”提示、无控制台错误。

### 关键浏览器证据

1. 外部 Codex 持有 writer 时，页面显示“其他 Codex 客户端正在使用 · Fleet 只读同步”和“Codex Desktop 正在输出”；输入可编辑，但没有“释放会话”和“停止生成”。
2. 浏览器提交排队消息后仅渲染一个用户消息；确认卡先仅有“等待并发送 / 强制接管 / 取消”。选择等待后变为“已由服务器排队”，仅保留“强制接管 / 取消”。
3. 刷新会清空当前页面选择，但重新打开同一会话后，服务端队列、确认按钮与单条消息完整恢复。
4. 外部 Codex 正常完成后，无需刷新即从外部占用切换为 Fleet 占用，排队卡消失；浏览器点击“释放会话”后显示“Fleet 只读，Codex 可接管”，输入、附件、审批、模型和发送均禁用；“恢复 Fleet 写入”后恢复可用。
5. fleet-agent 停止 13 秒后，页面显示“会话控制状态不可确认 · 正在重连”，不再显示旧外部占用，全部 mutation 控件禁用；agent 恢复后约 1.5 秒退出重连态。
6. 全流程浏览器控制台没有 error 或 warning；加载资源为 Dashboard PWA v116。

### 未通过项

#### UAT-D01（阻断）：外部 writer 进程异常退出后留下服务端幽灵占用

- `.2` 上真实 Codex CLI 已先被浏览器确认持有 writer；随后精确终止持锁 PID。
- `lsof` 确认 lock 文件无 holder，`pgrep` 确认 Codex CLI 与 `sleep 90` 均不存在，fleet-agent 健康。
- 浏览器连续 60 秒仍显示“其他 Codex 客户端正在使用 · Fleet 只读同步 / Codex Desktop 正在输出”；重启 fleet-agent 后仍恢复为同一错误状态。
- 只有再次用外部 Codex resume 并让一个新 turn 正常完成后，页面才在约 1.2 秒内清除外部占用。
- 代码辅证：当前 `Control` 在 rollout 仍为 active 且找不到物理 lock owner 时仍回退为 `desktop`；定时 orphan reaper 只枚举 Fleet sidecar writer，没有覆盖外部 writer。这会让服务端队列永久等待一个已不存在的进程。

#### UAT-D02（已撤销）：观察窗口不足被误判为 Fleet 静默失败

- 事后读取同一真实 UAT thread 的归档 rollout：浏览器独立 Fleet 消息写入时间为 `10:26:54.851Z`，助手 `UAT_FLEET_REPLY_DONE` 写入时间为 `10:28:35.249Z`，`task_complete` 为 `10:28:35.550Z`。
- 实际首 token 等待约 100.4 秒，turn 正常完成且有助手回复，不存在静默失败；原观察在回复到达前结束，因此 D02 不作为产品缺陷，也不据此增加错误协议。
- UAT-01 和 UAT-05 的未覆盖回复断言来自测试人员主动停止/释放 turn，保留为“部分通过”仅表示用例未完整执行，不表示实现失败。

### 与首次 UAT 的对比

1. 首次 UAT 的 D01 会在物理进程和 lock holder 都消失后永久保留 `desktop` 占用；修复后，服务端以真实 lock holder 为第一证据，并覆盖直接 CLI “没有 lock、但持有 rollout”的实际行为，异常退出后在下一轮服务端检测中回收。
2. 第一版修复只看物理 lock，把 Fleet 新建 thread 的首个无 lock turn 误判为空闲。真实浏览器回归捕获了这个退化；最终实现仅在 `agentID + turnID + Fleet owner` 全部匹配时保留服务端逻辑 lease，外部残留不能借此长期占用。
3. 首次 UAT 的 Dashboard v116 在部分结构化错误上可能渲染 `[object Object]`；v117 统一提取可读错误，成功重试后清除旧错误。本轮浏览器实测没有对象字符串或控制台异常。
4. 原 UAT-08 现已通过。修复后回归覆盖了“外部 writer 检出 → 浏览器排队 → 进程异常退出 → 服务端回收 → 自动投递 → 回复完成 → writer 释放”的完整用户路径，满足本轮放行标准。
